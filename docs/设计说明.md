# WebVault 设计说明

写给要读源码、改代码、或者评估「这东西能不能用在生产里」的人。这里讲清楚每个模块的取舍，以及哪些地方是刻意的妥协、哪些地方现在确实是坏的。

版本：v1.0.0。

---

## 1. 硬约束

这些约束决定了后面所有的设计，改动它们等于换一个产品：

| 约束 | 含义 |
|---|---|
| **零第三方依赖** | 只用标准库（`urllib`、`http.server`、`html.parser`、`re`、`json`、`base64`、`gzip`、`zlib`）。`lxml` / `Pillow` 存在时走增强路径，但**把它们卸掉之后功能一个都不少**——只是解析慢一点、图片大一点 |
| **产物是真·单文件** | 断网可开、可移动、可十年后打开。没有 `_files` 目录 |
| **永不抛异常** | 所有对外入口的失败都通过返回值表达（`ok=False` + `error`）。调用方不需要 try/except |
| **只写输出目录** | 除了用户指定的 `-o`，不往任何地方写文件 |
| Python 3.8+ | 实际在 3.8.6 上跑通。用了 `from __future__ import annotations`，所以 `list` 这类内置泛型注解不报错 |

「零依赖」是**功能承诺**而不是优化目标。这条约束直接导致了自己写 HTML 解析器（见 §4）。

## 2. 架构与数据流

```
        webvault.py (CLI)              webvault-ui.py (HTTP, 默认 :8770)
         │            \                        /
         │             \                      /
         │              v                    v
         │           src/pipeline.py :: vault()  ← 唯一的编排入口
         │                      │
         │   ┌──────────┬───────┼───────────┬──────────────┐
         │   v          v       v           v              v
         │ fetch.py  parse.py  extract.py  inline.py   render.py
         │ 抓取/编码  DOM 树   正文提取     资源内联    三种模式渲染
         │   │          │       │           │              │
         │   └──────────┴───────┴───────────┴──────────────┘
         │                      │
         │                   util.py  (文本归一化 / URL / 编码 / 体积格式化)
         │
         ├─→ discover.py :: discover()    从列表页里挑出文章链接
         ├─→ library.py  :: build_index() 把存下来的产物变成索引页
         └─→ watch.py    :: compare()     把正文记进 .webvault/，和上一版比对
```

模块之间**只通过 `Node` 树和 dataclass 结果对象通信**，没有全局状态、没有配置单例。`fetch.py` 不知道 `parse.py` 的存在，`parse.py` 不知道网络的存在。唯一的例外是 `inline.py` 需要抓取，所以它 import 了 `fetch.fetch`。

`discover.py`、`library.py` 和 `watch.py` 是后加的「外层」模块：它们不参与 `vault()` 的主流水线，只被 CLI 子命令（`webvault discover` / `webvault index` / `webvault diff`）和测试直接调用。`discover` 还会反过来调 `vault_many()`，把「发现链接 → 批量保存」串成一条龙；`watch` 的方向相反——是 `vault()` 在落盘之后反过来调它，这是唯一一处编排层向外层模块的反向依赖，因为变更追踪必须发生在保存成功之后。

### `vault()` 的六个阶段

```python
vault(url, *, mode="reader", inline_options=None, out_dir="", filename="",
      progress=None, timeout=25.0, write=True, keep_site_css=False,
      show_banner=True, extra_headers=None, verify_tls=False,
      track_changes=True) -> VaultResult
```

| # | 阶段 | 输入 → 输出 |
|---|---|---|
| 1 | **抓取** | `fetch(url)` → `FetchResult`（bytes、`final_url`、探测到的 `encoding`、重定向链） |
| 2 | **解析** | `parse(html_text)` → `Node` 文档根。这一步只为 full 模式取 meta，以及给 reader/data 的提取失败兜底 |
| 3 | **提取** | reader/data：`extract(html_text, base_url)` → `ExtractResult`（`root` = 正文容器）。full：不提取，只用 `get_meta_map()` 取标题和站点名 |
| 4 | **内联** | `Inliner(opts, base_url).inline_dom(work_root, base_url)` —— **就地修改 DOM**，返回 `AssetStats` |
| 5 | **同步** | reader/data 模式必须调 `refresh(ex)`，否则 `ex.html` / `ex.text` / 图片数还是内联前的旧快照 |
| 6 | **渲染 + 落盘** | `render_reader` / `render_full` / `build_data`，再由 `unique_path()` 决定文件名并写入 |

第 4 步和第 6 步之间还有一段只在 `keep_site_css=True`（且是 reader 模式）时执行：`collect_stylesheet_urls(ex, base_url)` 把提取阶段记下的外链样式表地址取出来，逐个交给 `inliner._get()` 抓取、`inliner._rewrite_css()` 重写（顺带内联样式表里的图片和字体），结果追加到 `ex.styles["inline"]`。这些 `<link>` 在提取阶段就已经被 `strip_junk()` 摘出树了，内联阶段看不见它们，所以必须单独补这一刀。

第 6 步（落盘成功）之后还有一段**变更追踪**，只在 `reader` / `data` 模式、`write=True` 且 `track_changes=True` 时执行：`block_text()` 把提取出来的正文按块切成行，`watch.record()` 写进 `<out_dir>/.webvault/`，再和上一版比一次，结果填进 `VaultResult.changed` / `change_stats` / `first_seen` / `history_key`。整段包在 try 里——追踪失败只打一行「变更追踪跳过：…」，保存结果不受影响。`full` 模式永不记录：整页快照没有提取正文，没有可比的文本。

三个关键点：

- **`work_root` 因模式而异**。reader/data 是**提取出来的正文容器**（`ex.root`），full 是**整个文档根**（`root`）。所以 reader 模式的内联只作用于正文，正文之外的图片根本不进预算——这既是省流量，也是 reader 产物比 full 小的主要原因。
- **内联改的是树，不是字符串**。`inline.py` 全部通过 `Node.set()` / `_replace_node()` 操作 DOM，`ExtractResult.html` 是提取那一刻的快照，所以第 5 步的 `refresh()` 不是可选的。
- **实际解析了两次**。reader/data 模式下，第 2 步 `parse()` 和第 3 步 `extract()` 内部的 `parse()` 是两次独立解析（`extract` 不接收现成的树）。这是当前实现里最明显的一处冗余，优化方向是让 `extract` 接受一个可选的 `Node` 参数，通过 `chosen` 的 `.parent` 指针回溯到文档根即可复用它——`Node` 已经维护了 `parent`，改动量很小。

## 3. 抓取层 `fetch.py`

`urllib` 而不是 `requests`，所以重定向、编码、压缩、重试都得自己实现。

```python
def fetch(url: str, *, timeout: float = 20.0, headers: Optional[Dict[str, str]] = None,
          max_redirects: int = 8, retries: int = 2, insecure: bool = True,
          max_bytes: int = 32 * 1024 * 1024, referer: str = "") -> FetchResult
```

### 重定向自己跟

`_NoRedirect(HTTPRedirectHandler)` 的 `redirect_request()` 直接返回 `None`，屏蔽 urllib 内置跳转，改由 `fetch` 循环处理，这样能记录完整的跳转链（`FetchResult.redirects`）并在超限时给出明确错误。上限 8 跳，超出返回 `error="重定向次数过多"`。

`301/302/303/307/308` 都按普通跳转处理（不做 307/308 的方法保持语义区分，因为我们只发 GET，无所谓）。缺 `Location` 头会明确报错而不是死循环。

### 编码检测不依赖 chardet

`sniff_encoding(body, headers=None, declared="")` 的优先级链：

```
显式 declared 参数
  → BOM（EF BB BF → utf-8-sig；FF FE / FE FF → utf-16）
  → HTTP 头 Content-Type 里的 charset
  → <meta charset>（只看前 4 KB，两种正则形式：charset= 和 content="...charset=..."）
  → 严格 UTF-8 试解，成功即认定
  → 依次试 gbk / big5 / shift_jis / euc-kr
  → 兜底 utf-8
```

中文站点的实际价值在这一步：**大量老站点是 GBK 但没有任何声明**，HTTP 头也只写 `text/html`，最后只能靠「UTF-8 严格解失败 → 试 GBK」这条启发式救回来。`ENCODING_ALIASES` 把 `gb2312`/`chinese`/`csgb2312` 都映射到 `gbk`（Python 的 `gb2312` 编解码器对实际网页里的生僻字太严格，用 `gbk` 更宽容）。

`decode_bytes()` 还有第二层兜底：`enc → utf-8 → gbk → latin-1 → utf-8(errors="replace")`，任何输入都不会抛异常。

### 错误处理的哲学

- **4xx/5xx 也把 body 读回来**。403 的错误页、404 页有时包含有用信息，而且比「什么都没有」更好判断。返回 `ok=False` + `error="HTTP 403 Forbidden"`，但 `body` 有值。`pipeline` 的判断是 `if not fr.ok and not fr.body` 才算彻底失败——**有 body 就继续往下走**，所以一个 403 页面照样会产出 HTML（通常是垃圾，但这是刻意的选择）。
- **只对连接类错误重试**（`URLError` / `socket.timeout` / `SSLError` / `OSError`），退避 `0.4 * (attempt+1)` 秒。HTTP 错误码不重试——那没意义。
- `max_bytes` 默认 32 MB，`resp.read(max_bytes)` 直接截断超大的页面。

### 两个安全/性能取舍

```python
def _ssl_context(insecure: bool = True):
    ...
    ctx.check_hostname = False
    ctx.verify_mode = ssl.CERT_NONE
```

**默认不校验 TLS 证书**（`insecure=True` / `CERT_NONE`）。理由写在注释里：「抓公开网页时证书问题很常见，不值得为此失败」——过期证书、自签名证书、链不全的站点在小站和国内站点上确实常见。代价是容易受中间人攻击。

需要严格校验时有三个入口：CLI 加 `--verify-tls`，`vault(..., verify_tls=True)`，或者直接调 `fetch(..., insecure=False)`。这个开关会一路传到内联器（`InlineOptions.verify_tls`），所以页面本身和它内联的资源用的是同一套策略。

请求头固定带 `Connection: close`。也就是**每个资源一条新连接，没有 keep-alive**。内联几十张图时这是明显的性能损失（每次都要 TLS 握手），换来的是实现简单、不会被服务端的空闲超时策略搞乱。如果要把内联速度再提一档，这里是收益最大的地方。

`DEFAULT_UA` 是硬编码的 Chrome 124 UA。**不提供 `--user-agent` 参数**——CLI 层没有暴露，只有 Python API 能通过 `extra_headers` 覆盖。

## 4. 解析层 `parse.py` —— 为什么不用 lxml

这是整份代码里最"重"的一个模块（约 550 行），也是「零依赖」承诺代价的直接体现。

### 不用 lxml 的理由

1. **分发问题**。目标用户可能在没有编译器的 Windows 机器上、或者内网离线环境里跑。`pip install lxml` 需要 wheel 或编译工具链，`html5lib` 是纯 Python 但很慢。要求用户先装环境，就违背了「下载解压就能用」。
2. **只有标准库的机器必须能跑**。这是承诺，不是偏好。
3. **需求比通用解析器窄**。我们要的不是「完美还原浏览器树」，而是「够用的树 + 能被容错地遍历」。HTML5 规范的树构建算法（插入模式、adoption agency algorithm 等）有几千行，我们不需要那套精度。

于是策略是：**`html.parser` 提供词法层（已经是标准库、经过验证的），自己写树构建层**。`parse()` 的默认 `fast=True` 会在 `lxml` 可用时走 `parse_html_fast()`，把 lxml 树转换成**同一套 `Node` 结构**，所以上层代码完全不知道底层是谁解析的。lxml 路径抛异常时自动 `return parse_html(html)` 退回纯标准库实现。

### 容错机制

真实网页的破损方式是有限的几种，逐一对付：

**① 隐式闭合规则**

`IMPLICIT_CLOSE` 是一张「遇到 key 时，栈里这些 tag 该让位」的表：

```python
IMPLICIT_CLOSE = {
    "li": frozenset(["li"]),
    "dt": frozenset(["dt", "dd"]),
    "tr": frozenset(["tr", "td", "th"]),
    "td": frozenset(["td", "th"]),
    "p":  frozenset(["p"]),
    ...
}
```

难点在于**不能只看栈顶**。以 `<table><tr><td>1<td>2<tr>...` 为例，遇到第二个 `<tr>` 时栈是 `[table, tr, td]`，必须一路向上把 `td` 和 `tr` 都弹掉，新的 `tr` 才能成为第一个 `tr` 的兄弟而不是 `td` 的孩子。所以 `_auto_close()` 的算法是：

```
从栈顶往下扫：
  遇到与当前 tag 同名的元素 → 记下位置并停止（新元素成为它的兄弟）
  遇到表里列出的"让位者"     → 只记下第一个位置，继续向上找同名元素
  遇到容器边界（table/body/html/ul/ol/dl/select）→ 停止上溯
最后把记下的位置及以上的所有元素弹出
```

`<p>` 的规则独立处理：`BLOCK_FOR_P` 列出了所有块级标签，遇到它们时如果栈里有 `p` 就闭合 `p`（遇到 `body/html/div/td/li/blockquote` 边界则停）。这解决了最常见的 `<p>a<p>b` 和 `<p>x<div>y</div>`。

**② 破损属性引号修复**

最致命的一类破损是属性值引号没闭合：

```html
<div class="a><p>整页后面所有内容都被吞掉</p>
```

`html.parser` 会把 `class` 的值一直吃到下一个引号，可能吃掉整页。`_repair_attrs()` 用正则给这种属性补上引号：

```python
_UNCLOSED_ATTR   = re.compile(r'=\s*"([^"<>]*?)(?=[<>])')
_UNCLOSED_ATTR_S = re.compile(r"=\s*'([^'<>]*?)(?=[<>])")
```

只在**引号总数是奇数**时才动手（先做一次便宜的 `count('"') % 2` 判断），避免对正常文档做无谓的改写和风险。

修复后重新解析一遍，并且**只在新的树节点更多时才采用它**：

```python
if failed or len(builder.root.children) == 0:
    repaired = _repair_attrs(html)
    if repaired != html:
        ...
        if len(list(b2.root.iter())) > len(list(builder.root.iter())):
            return b2.root
```

「节点更多才采用」是一个廉价但有效的护栏——修复可能引入误判，用「结果是否更好」来裁决，比信任正则更稳。

**③ 未匹配的结束标签直接忽略**

```python
def handle_endtag(self, tag):
    for i in range(len(self.stack) - 1, 0, -1):
        if self.stack[i].tag == tag:
            del self.stack[i:]
            return
    # 没找到匹配 —— 真实世界的 HTML 经常这样，忽略即可
```

`</div>` 多出来的情况极其普遍，忽略比报错合理。

**④ 全程不抛异常**

`parse_html()` 把 `builder.feed()` / `builder.close()` 包在 try 里，失败也返回当前已构建的树。`parse()` 是这条承诺的对外出口：**宁可产出一棵粗糙的树，也不能让整个流程挂掉**。

### 已知的粗糙之处

- **注释、DOCTYPE、处理指令全部丢弃**（`handle_comment` / `handle_decl` / `handle_pi` / `unknown_decl` 都是 `pass`）。所以 full 模式**不是字节级保真**——条件注释、SSI 指令、DOCTYPE 声明都会消失，输出统一是 `<!DOCTYPE html>`。
- **`Node.start` / `Node.end` 目前不可用**。`__init__` 里初始化为 `-1`，`_flush_text()` 里赋的是 `self.getpos()[1]`——**那是列号，不是文档绝对偏移**；`end` 从来没有被赋过值，永远是 `-1`。docstring 里「记录每个节点的源码起止位置，便于原样保留未知片段」描述的是**意图**，不是现状。好消息是管线里没有任何代码依赖这两个字段，所以它们目前只是两个没用的槽位（`__slots__` 里省不掉）。
- **`RAW_TEXT_ELEMENTS` 常量定义了但没用到**。`script` / `style` / `textarea` / `title` 的原始文本处理是 `html.parser` 自己的 `CDATA_CONTENT_ELEMENTS` 在管，不需要我们干预。
- **`CONTENT_TAGS`、`DEFAULT_DROP_TAGS` 定义了但没用到**。实际用的是 `extract.py` 里自己的 `JUNK_TAGS`。这两组常量是从早期版本留下来的。
- **`get_base_href()`、`collect_links()`、`collect_images()` 定义了但没人调用**（连测试都没有）。注意 `get_base_href` 未被使用意味着 **`<base href>` 被完全忽略**——如果站点用 `<base>` 改写相对路径基准，资源解析会错。这是个真实的功能空缺，触发条件不常见但存在。
- **lxml 快路径不做属性修复**，所以它和纯标准库路径在破损 HTML 上的结果可能不同。这是「增强路径」的固有代价。

## 5. 提取层 `extract.py` —— 打分模型

一脉相承自 Arc90 Readability，但针对中文页面重调了信号。

### 候选集合

只有这几种标签参与打分：`div`、`article`、`main`、`section`、`td`、`body`、`blockquote`，且加权文本量必须 `>= 40`（`text_length` 的单位见下）。这一刀切掉了绝大多数噪声节点。

### 打分信号（全部，带权重）

```python
score = 0.0
score += (tl ** 0.5) * 1.6                 # 文本量，开方抑制超大容器
if punct > 0.02:
    score += punct * 180.0                 # 标点密度：自然语言的标志
score -= ld * 120.0                        # 链接密度惩罚
if ld > 0.6:
    score -= 100.0                         # 导航/列表页再加一刀
score += _hint_score(node)                 # class/id 词表，见下
score += 60.0   if tag == "article"
score += 45.0   elif tag == "main"
score += 5.0    elif tag in ("div", "section")
score += good_paras * 8.0                  # good_paras = 通过可读性判断的 <p> 数
if good_paras >= 3:
    score += 25.0
if imgs == 0 and tl > 4000 and good_paras < 3:
    score -= 30.0                          # 无图 + 大文本 + 少段落 = 文字墙
```

其中：

- `tl` 是 `text_length()` 的结果，**不是字符数**：`int(汉字数 * 1.6 + 其他 * 0.6)`。汉字（`\u4e00-\u9fff` 和 `\u3400-\u4dbf`）按 1.6 计，其余字符（含英文、数字、标点、空白）按 0.6 计。
- `punct` 是 `punctuation_density()`：`。！？；.!?;…` 加上 `，,、：:` 在文本里的占比。阈值 `0.02` 是「低于这个比例就不像人写的句子」。0.05 的密度贡献约 +9 分，量级是温和的加分而非决定性的。
- `ld` 是 `link_density()`：节点内所有 `<a>` 的文本长度除以节点总文本长度，`min(1.0, ...)` 封顶。
- `_hint_score()` 对 `id` 和 `class` 拼接后的小写串做**子串计数**：`POSITIVE_HINTS` 里每命中一个词 **+25**，`NEGATIVE_HINTS` 里每命中一个词 **-30**。

这个"每词独立加减"的设计有个直接后果值得注意：`class="content-nav"` 会同时命中 `content`（+25）和 `nav`（-30），净 **-5**。也就是说负向词的权重被刻意调得更高（30 > 25），让「既像正文又像导航」的容器偏向被判为噪声。词表里两类词汇故意重叠（`header`、`content` 等）就是为了让这种抵消发生。

### 选择与扩展

```python
def pick_best(candidates: List[Candidate]) -> Optional[Candidate]
def expand_with_siblings(root: Node, best: Candidate, threshold: float = 0.22) -> Node
```

`pick_best()` 就是取最高分，**得分 `<= 0` 时返回 `None`**（宁可走 fallback 也不要一个明显是垃圾的容器）。

`expand_with_siblings()` 的名字有误导性——它**并没有合并兄弟节点**。实际逻辑只有一条：如果父节点的文本量比最佳候选多 1.6 倍以上，且父节点是 `div/article/main/section/body`，就改用父节点（还会看一眼祖父节点：如果祖父的文本量不到父节点的 1.5 倍，仍然用父节点）。目的是对付 `<div class="content"><p>…</p></div>` 加若干平行 `div` 这类「正文被切成多块」的结构——只取最高的那一块会漏掉后续段落。

两个参数是死参数：**`threshold` 从未被读取，`root` 也从未被使用**。

### 二次清洗

选中的容器里仍会混进导航条、分享按钮、「上一篇/下一篇」。`clean_content()` 用三条线索挑掉：

| 规则 | 条件 |
|---|---|
| 结构标签 | 子孙里的 `nav`/`footer`/`header`/`aside`/`menu` 直接删 |
| 词表 + 链接密度 | `class`/`id` 命中 `NEGATIVE_HINTS` 且 文本 < 400 **且** 链接密度 > 0.15 |
| 纯链接块 | 链接密度 > 0.75 且 文本 < 300 |
| 链接列表 | `<a>` 数 >= 4 且 标点 <= 1 且 文本 < 400 |
| 样板文字 | 匹配 `BOILERPLATE_PATTERNS` 的**孤立文本节点**（「阅读全文」「点击查看」「上一篇」等） |

`<p>` 是例外：段落是正文的基本单位，真实文章里到处都是整段只放一个链接的「延伸阅读」「参考资料」，所以 `<p>` 不走链接密度那两条规则，只有它自己带上噪音 `class`/`id` 且文本 < 200 时才删。

然后 `_trim_edges()` 从首尾反复剥掉低质量块（最多 6 轮），`_is_low_quality_block()` 的判定是：

- `h1/h2/h3/table/pre/blockquote/figure/img` → 永不删（可能是正文的结构部分）
- `<p>` → 只按样板文案判断（`_is_boilerplate()`），不因为链接密度高而删
- 加权文本量 `>= 600` → 不删
- `class`/`id` 命中 `nav`/`pager`/`pagination`/`share`/`breadcrumb`/`上一篇`/`下一篇`/`相关`/`推荐`/`ad-` → 删
- 链接密度 > 0.5 → 删
- 文本 < 40 且无任何标点 → 删

最后 `prune_empty()` 递归删掉空容器（但保留 `img/br/hr/td/th/li/blockquote/pre`）。`prune_empty` 的 `keep_media` 参数**没有被使用**——无论传什么，保留的标签集合都是写死的那一组。

### 中文适配

三处针对性调整，都写在模块 docstring 里：

1. **不用「词数」估长度**。中文没有空格分词，所以用「汉字数 + 标点」加权（`text_length`）。
2. **`is_probably_readable()` 对中文放宽**。中文只要 `>= 8` 个汉字且有句末标点（或逗号/顿号），或者长度 `>= 30`，就算可读；西文要求 `>= 6` 个空格且有 `.!?`，或者长度 `>= 90`。
3. **链接密度阈值偏高**。中文导航常常一个链接包住好几个字，同样的链接密度下中文页面的数值天然比英文高，所以惩罚阈值不能照搬 Readability 的默认值。

### 置信度与回退

```python
ratio = best.text_len / total_text          # 选中部分占页面总文本的比例
confidence = min(1.0, (best.score / 400.0) * 0.6 + ratio * 0.4)
```

得分和覆盖比例各占六四开。**回退条件**是「没选出候选」或「选中容器的加权文本量 < 60」，此时退回 `<body>`（没有 body 就退回整棵树），`method="fallback"`，并把置信度压到 `min(confidence, 0.25)`。

`method` 最终只会是 `"readability"` 或 `"fallback"`。`ExtractResult` 支持 `"error"`（`pipeline` 在 `extract()` 抛异常时构造）和 `"full"`（full 模式构造），但前者会被立即改写成 `fallback`，后者不产出 JSON，所以都在对外结果里看不到。

### 作者名（byline）为什么这么啰嗦

`_find_byline()` 有 40 行，因为最直觉的做法（搜 `class` 含 `author` 的元素）会抓到**评论区的用户名**。所以策略是分三层，逐层收紧：

1. **meta 优先**：`article:author` / `author` / `og:article:author` / `twitter:creator`。值是 URL 时取最后一段路径（作者主页链接的常见形态）。
2. **`rel="author"` 链接**。
3. **强信号 class**：`byline` / `author-name` / `post-author` / `article-author` / `entry-author` / `writer` / `作者` 等，且**显式排除**含 `comment`/`reply`/`remark`/`review`/`评论`/`回复` 的元素。

所有候选最后都要过 `_byline_ok()`：长度 1~40、不含句读（`_BYLINE_REJECT`）、不是样板文字、不含 `http`、不含 `@`、不是纯数字、汉字数不超过 12、空格数不超过 4。这些条件是一堆「抓到句子或评论者」的实际案例倒推出来的。

## 6. 内联层 `inline.py` —— 策略与预算

`inline_dom(root, base_url="")` **就地**处理整棵树。分三步：收集 → 并发预抓 → 顺序替换。

### 收集阶段

只对这几类节点建 job：

| 节点 | 处理属性 |
|---|---|
| `<img>` | `src` / `data-src` / `data-original` / `data-lazy-src` / `data-echo`；有 `srcset` 时用 `_pick_srcset()` 挑**最大的一档**覆盖 `src` |
| `<source>` | `srcset` / `data-srcset` |
| `<video>` / `<audio>` | 只处理 `poster`（媒体文件本身不内联） |
| `<link rel=stylesheet>` | 抓回来内联成 `<style>` |
| `<link rel=icon>` | 内联成 data URI 写回 `href` |

懒加载属性在这一步**无条件清理**（`data-src` / `data-original` / `data-lazy-src` / `data-echo` / `data-srcset` / `loading` / `srcset`），即使后面内联失败也会清掉——目的是产物里不留一堆没人用的 `data-*`。

字体没有自己的收集分支，它们藏在 CSS 的 `url()` 里，到替换阶段才被识别。`--no-fonts`（即 `InlineOptions.fonts=False`）在 `_inline_one()` 里生效：`_is_font(mime, url)` 认出字体资源（MIME 含 `font`，或 URL 后缀是 `.woff` / `.woff2` / `.ttf` / `.otf` / `.eot`）后直接返回空串，资源计入 `skipped`、`skipped_urls` 里留一条 `(font skipped)`，而 CSS 里那个 `url()` 被改写成**绝对地址**——不会变成坏链，只是仍然需要联网。字体判定发生在扣预算之前，所以被跳过的字体不占预算。

`_pick_srcset()` 的挑选逻辑：解析 `SRCSET_RE`，按数值打分（`w` 单位直接用数字，`x` 单位乘 1000 以拉开与宽度描述符的量级），取分最高的一档。

### 并发预抓

```python
if opt.workers > 1 and len(jobs) > 1:
    uniq = [...]                      # 按 normalize_url_for_dedup 去重
    with ThreadPoolExecutor(max_workers=max(1, opt.workers)) as pool:
        futs = {pool.submit(self._get, u): u for u in uniq}
```

默认 `workers=16`（I/O 密集，16 个线程够用）。这一步只负责把内容**灌进缓存**（`self._cache`），**不消费预算**——预算是在后面的顺序替换阶段扣的。

这个设计决定了预算分配是**确定性的**：`jobs` 按 DOM 顺序排列，替换循环也是按这个顺序走，所以「哪些资源能拿到预算」在同样输入下永远一样，不受线程调度影响。

### 缓存与去重

```python
def _get(self, url: str) -> Optional[bytes]
```

- 键是 `normalize_url_for_dedup(url)`——去掉 fragment，并丢掉 `utm_*`/`fbclid`/`gclid`/`spm`/`from`/`share_*` 这些追踪参数。所以 `?utm_source=x` 和 `?utm_source=y` 的同一张图只抓一次。
- **失败的资源也会被缓存为 `None`**，避免同一个失效地址被反复重试。
- 缓存读写由 `self._lock` 保护（`Inliner` 声明是线程安全的）。
- 资源抓取用 `retries=1`（共 2 次尝试），比页面抓取的 2 次略少，因为资源数量多。
- 单个资源读取上限就是 `max_asset_bytes`。

### 预算模型

```python
self._budget_left = self.opt.max_total_bytes     # 默认 24 MB

def _take_budget(self, n: int) -> bool:
    cost = _base64_size(n)                       # ((n + 2) // 3) * 4 + 48
    with self._budget_lock:
        if cost > self._budget_left:
            return False                          # 不够就整块拒绝，不部分接受
        self._budget_left -= cost
        self.stats.budget_spent += cost
        return True
```

四个必须知道的行为：

1. **全局共享，不按类型分配**。图片、CSS、字体、脚本共用一个池子。
2. **扣的是内联之后的体积**。`_base64_size(n)` 把原始字节换算成 base64 之后的长度再加上 data URI 前缀的长度，所以 `--max-total` 是**产物体积的上限**，不是原始字节的上限（早期版本按原始字节扣，产物会比设定值大三分之一，现在不会了）。唯一的例外是 `--scripts inline` 那条路，它仍然按 `len(js)` 扣——那是字符数不是字节数，非 ASCII 的 JS 会少扣一点。
3. **图片先压缩后扣费**。`_process_image()` 在 `_take_budget()` 之前执行，所以扣的是压缩后的大小（有 Pillow 时）。
4. **扣了不还**。`_give_budget()` 方法存在（会同时回退 `budget_spent`）但**从未被调用**——没有"回滚"路径。资源替换是单向的，不存在先占位后释放。

`AssetStats` 会同时记下 `budget_spent` 和 `budget_total`，所以 `summary()` 除了「抓取/内联/跳过/失败」之外还会带一段 `预算 X/Y (Z%)`。

另外注意 `max_asset_bytes` **同时是单个资源的读取上限**（`_get()` 里把它当作 `fetch(max_bytes=...)`）。副作用是：超过上限的资源不会走到「跳过」分支，而是被 `resp.read(max_bytes)` 截断到上限之后照常内联——`_inline_one()` 里那句 `len(data) > max_asset_bytes` 在真实网络路径下几乎不会命中（只有测试里替换过 `_get()`、或者响应经 gzip 解压后膨胀时才会）。产物里因此可能出现一个不完整的图。

预算耗尽只是记 `stats.skipped += 1` 并往 `skipped_urls` 里塞一条 `(budget) <url>`，**不报错、不影响退出码**。上限 60 条。

### 超限资源的降级行为

这是「单文件承诺」最脆弱的地方：

| 情况 | 结果 |
|---|---|
| `<img>` 内联失败（超 `max_asset`、超预算、抓取失败） | `src` 被改写成**绝对 URL** |
| `<img>` 因为 `--local-only` 被排除 | 根本没进 job，`src` 保持原值（可能是相对路径） |
| `<link rel=stylesheet>` 抓取失败 | `href` 改写成绝对 URL，标签保留 |
| CSS 里的 `url(...)` 抓取失败 | 改写成绝对 URL（注释写的是「至少不会 404」） |
| `<script src>` 在 `inline` 模式下抓取失败 | `src` 改写成绝对 URL，标签保留 |

所以**「真·单文件」的成立条件是「跳过数 + 失败数 = 0」**。有降级项时文件里就留着需要联网的引用。这是刻意的取舍：宁可留一个能用的外链，也不要留一个坏掉的相对路径。

### CSS 递归

`_rewrite_css(css, css_url, depth=0)` 做两件事：

1. **`@import` 就地展开**成被导入文件的内容，**深度上限 4 层**（`if depth > 4: return css`），带 `media` 属性时包一层 `@media`。
2. **`url(...)` 全部内联**。`CSS_URL_RE` 同时支持 `url(x)` / `url("x")` / `url('x')` 三种写法；`data:` 和 `#` 开头的跳过；`is_fetchable()` 和 `_url_allowed()` 两道过滤。

`@charset` 声明会被删掉——内联进 HTML 之后它既无意义又可能引发解码歧义。

处理的入口有三处：`<link rel=stylesheet>`（整个替换成 `<style>`）、树里所有 `<style>` 标签的文本子节点、以及所有元素的**行内 `style` 属性**（只有含 `url(` 时才处理）。

字体没有独立分支，它就是在 CSS 里被 `url()` 引用然后走这条路。`woff`/`woff2`/`ttf`/`otf` 靠魔数识别（`wOFF` / `wOF2` / `OTTO` / `\x00\x01\x00\x00`）。要拦字体用 `--no-fonts`（见上），不必动 `--no-css`。

### 图片处理决策树

```python
def _process_image(self, data: bytes, mime: str) -> Tuple[bytes, str]
```

```
compress_images 关了            → 原样返回
mime 是 svg/gif/webp            → 原样返回（重编码会破坏矢量性或动画）
len(data) < 24 KB               → 原样返回（压了也不划算）
Pillow 不可用                    → 原样返回
宽度 > image_max_width          → LANCZOS 等比缩小
  有 alpha 通道                 → 存 PNG(optimize)，只在更小时才采用
  其他                          → 转 RGB 存 JPEG(quality=82, optimize, progressive)，
                                  只在更小时才采用
```

「只在更小时才采用」是关键的保护：重新编码不保证变小，尤其是已经优化过的图。`jpeg_quality=82` 写死在 `InlineOptions` 里，CLI 没有暴露。

### 脚本策略

```python
def _handle_scripts(self, root: Node, base: str) -> None
```

| 模式 | 行为 |
|---|---|
| `keep` | 直接 `return`，什么都不做 |
| `drop` | 删掉所有 `<script>`（不论内外链） |
| `inline` | 外链脚本抓回来塞进标签并删掉 `src`；内联脚本保留不动 |

`inline` 模式的几个细节：抓取失败的退回绝对 URL；超过 `max_asset_bytes` 的退回绝对 URL；**扣预算用的是 `len(js)`，那是字符数不是字节数**——非 ASCII 的 JS 会被少扣一点，属于小瑕疵；内联内容**不做任何改写**，等于把第三方 JS 原封不动搬进你的存档，这是安全上的取舍。

## 7. 渲染层 `render.py`

| | reader | full | data |
|---|---|---|---|
| 输入 | `ExtractResult`（正文容器） | 整个文档根 | `ExtractResult` |
| 输出 | 完整 HTML 文档 | 完整 HTML 文档 | dict → JSON |
| 样式 | 内置 `READER_CSS`（约 70 行）；加 `--keep-site-css` 时把原站 CSS 拼在它后面 | 页面原有样式，全部内联 | 无 |
| 元信息 | 顶部 `.wv-meta` 块 + 底部 footer + `wv-mode` | `<meta name="wv-source">` / `wv-captured` / `wv-mode` + 底部来源条 | JSON 字段 |
| 暗色模式 | 支持（`prefers-color-scheme`） | 跟随页面本身 | — |

### reader 的原站样式（`--keep-site-css`）

默认 reader 只用内置排版。带上 `--keep-site-css` 之后，`render_reader()` 会把站点样式拼在内置 `READER_CSS` 后面（写在同一个 `<style>` 块里）——`_extract_style_texts(ex)` 取 `ex.styles["inline"]`（提取阶段用 `keep_styles=True` 收集的 `<style>` 原文），再顺手把树上还活着的 `<style>` 节点也带上；外链样式表由 `pipeline` 补抓后追加进同一个列表（见 §2）。

代价要清楚：这些规则排在内置排版之后，选择器特异性又常常更高，所以站点的定位、栅格、字号会直接压过 reader 的排版——「正文 + 原站样式」意味着放弃「干净」这个卖点，原站样式和内置排版打架时以内置排版为底、以站点规则为准。样式表里引用的图片和字体也会一起内联，产物会明显变大。

这个开关只在 **reader 模式**生效：full 模式本来就保留 `<style>` / `<link>`，data 模式不产出页面，两者都不看它。另外 `pipeline` 的补抓那一步不看 `InlineOptions.css`，所以 `--keep-site-css --no-css` 仍然会把外链样式表抓回来（同时也内联样式表里的图片）。

### reader 的元信息块

`_format_meta_block()` 拼出：来源站点、作者、抓取时间、原文链接（`rel="noopener noreferrer"`）、摘要（截断到 280 字符），以及一排 badge：`正文 N 字`、`图 N`、`置信度 NN%`、以及内联统计行。所有动态文本都过 `escape()`。

**注意 reader 从 `ex.root`（活 DOM）序列化，而不是 `ex.html`（快照）**——这行注释在代码里专门写明了，因为用快照会导致内联结果全部丢失：

```python
if ex.root is not None:
    content = ex.root.to_html()
else:
    content = ex.html or ""
```

### `wv-mode`：产物自己说清是哪种模式

`render_reader()` 和 `render_full()` 都会在 `<head>` 里写一行 `<meta name="wv-mode" content="reader">` / `content="full"`；data 模式的 `.json` 没有 HTML 头，`library.py` 读 JSON 时直接把 `wv-mode` 记成 `data`。

这一行只为一件事服务：`index` 的分类。书库扫描只读文件前 200 KB、用正则抓 meta，不重新解析整棵树，所以模式只能从 meta 里来。在此之前 reader / full 的模板都不写这个 meta，`Entry.mode` 只能兜底成 `reader`——索引页按 `full` 筛选时永远筛不出东西，这是一个真实的坏功能。现在三种模式的产物都能被正确标注，筛选才成立。

`FULL_TEMPLATE` 里也补了同样的 meta，但它仍然是一段没被使用的模板（见 §8.4）。

### full 的来源条

`BANNER_CSS` + `BANNER_HTML` 注入到 `body` 末尾，`position: fixed` 贴底，`z-index: 2147483647`（int32 最大值，确保压过页面自己的浮层）。带一个「隐藏」按钮，内联 `onclick` 同时把 `body` 的 `padding-bottom` 归零。`body{padding-bottom:38px !important}` 给来源条让位。

`render_full()` 不用 `FULL_TEMPLATE`——那个常量定义了但**从未被使用**，实际输出是用 `%` 手工拼的字符串（`<!DOCTYPE html>\n<html lang=...>` + head + body 的序列化结果），`wv-source` / `wv-captured` / `wv-mode` 三个 meta 是在 `head_el` 上 `append()` 出来的。`FULL_TEMPLATE` 是早期版本遗留，里面也补了同样的三个 meta 只是为了「读代码时看不出差异」，它仍然不参与任何一次渲染。

full 模式还会做结构补全：没有 `<body>` 就造一个并把游离的顶层节点搬进去，没有 `<head>` 也造一个。

### data 模式

`build_data()` 的完整字段说明见[命令行手册](命令行手册.md#data-模式的-json-结构)。实现上值得注意的两点：

- `html` / `text` / `images` / `links` / `tables` / `headings` **全部从 `ex.root`（内联后的活 DOM）读取**，所以 `images[].src` 默认是 data URI，`inline` 字段就是 `src.startswith("data:")` 的结果。
- `url` 和 `final_url` 都被赋成传进来的 `source_url`（即重定向后的最终地址），`pipeline` 再额外补一个 `requested_url` 记录用户的原始输入。所以想知道原始 URL 要看 `requested_url`。

`render()` 这个统一入口（按 mode 分发）定义了、导出了，但**管线没走它**——`pipeline` 直接调 `render_full` / `render_reader` / `build_data`。`render_data()` 和 `inline_all()`、`extract_text()`、`fetch_bytes()`、`_looks_like_html()` 同样是「提供了但没人调用」的便利函数。

## 8. 已知限制与取舍

按性质分四类。**这里列的都是当前代码的真实行为**，不是「以后可能」。

### 8.1 功能空缺

| 空缺 | 原因 / 影响 |
|---|---|
| **`--max-width` / `--no-compress` 依赖 Pillow** | 没装 Pillow 时这两个参数是空操作，图片原样内联 |
| **`<base href>` 被忽略** | `get_base_href()` 存在但没人调用。用 `<base>` 改写相对路径基准的站点，资源解析会错 |
| **不执行 JavaScript** | 没有 JS 引擎。SPA 只能抓到空壳，提取会退回整页 |
| **无 Cookie / 无会话 / 无代理** | 抓取层只有固定的几个请求头。CLI 没有 `--user-agent` / `--cookie` / `--proxy`；Python API 只能通过 `extra_headers` 加头，加不了代理 |
| **不内联媒体文件** | `<video>` / `<audio>` 的 `src` 不处理，只处理 `poster` 图 |
| **表格丢失结构** | `tables` 是二维字符串数组，`<th>` 和 `<td>` 混在一起，`rowspan`/`colspan` 不展开、不保留表头语义 |
| **`word_count` 不是字数** | 是 `int(汉字 * 1.6 + 其他 * 0.6)` 的加权值，中文加权长度，既不是字数也不是字符数 |
| **超过 `--max-asset` 的资源会被截断后照常内联** | 这个值同时被当作 `fetch(max_bytes=...)` 的读取上限，`_get()` 拿到的就已经是截断过的内容，所以「太大就跳过」那句判断在真实网络路径下几乎不触发。要避免产物里出现不完整的图，就把 `--max-asset` 设到足够大以覆盖目标站点的资源，或者用 `-m data --no-images` 只拿链接、不下载资源 |

> 早期版本里 `--keep-site-css` 和 `--no-fonts` 都是空开关——一个传下去了但样式早在提取阶段就被删干净，另一个的值根本没人读。现在两个都真实生效：`--keep-site-css` 的行为见 §7，`--no-fonts` 的行为见 §6。

### 8.2 行为与直觉不符的地方

| 现象 | 说明 |
|---|---|
| **批量模式忽略 `-n` / `--name`** | `vault_many()` 没有 `filename` 参数，所以批量时文件名一律由标题生成；CLI 会给一条 stderr 提示。`--keep-site-css` 和 `--no-banner` 现在会正常转发给每个 `vault()` 调用 |
| **批量模式拒绝 `--stdout`** | 多个 URL 时直接打印「--stdout 只支持单个 URL」并以退出码 2 退出（早期版本会静默写文件，还把汇总文字混进 stdout） |
| **`-q` 仍然打印汇总块** | 它只关掉横幅、进度行、跳过列表；`✔ 完成` 那一块不受 `verbose` 控制 |
| **`-n` 不补扩展名** | `-n 存档` 会得到名叫「存档」的文件，要写 `-n 存档.html` |
| **`--max-total` 现在是产物体积的上限** | 预算按 base64 之后的体积扣（见 §6），所以产物不会比上限大三分之一。另外 `--max-asset` 同时是单资源的读取上限，超限资源会被截断后内联（见 §8.1） |
| **reader 模式脚本策略无意义** | 提取阶段就把 `<script>` 当垃圾删了，`--scripts` 三个取值在 reader 下结果相同。`pipeline` 里那段「reader 默认 drop 脚本」的逻辑只在调用方完全不传 `inline_options` 时生效，CLI 永远会传，走不到 |
| **UI 的「干净排版（丢原站样式）」勾选框** | 语义是反的：勾上 = `keep_site_css=False`（只用内置排版），不勾 = `keep_site_css=True`（保留原站样式）。`/api/info` 里的 `clean_css_default` 固定返回 `False`，所以界面默认是**不勾**、也就是默认保留原站样式——这一点和 CLI 的默认相反 |
| **UI 超时来自请求** | 不再是写死的 25 秒：`_num()` 从请求里取 `timeout` 并夹在 5–120 秒之间，取不到或非法就用默认值 25 |
| **UI 的数字参数做了容错** | `max_total`（1–4096 MB）、`max_asset`（1–1024 MB）、`timeout`（5–120 秒）都走 `_num()`，`""` / `"abc"` / `null` 一律退回默认值，不会 500 |
| **UI 每次最多 60 个 URL** | 超出部分被静默截断（`urls = urls[:60]`），界面不会提示 |

### 8.3 性能与安全取舍

**性能**

- **每请求一条新连接**（`Connection: close`）。内联几十个资源时，TLS 握手的开销占大头，这是当前最容易优化的点。
- **reader/data 模式解析两次** HTML（`pipeline.parse()` 和 `extract()` 内部各一次）。
- **`Node` 用 `__slots__` 但没有索引**。`find()` / `find_all()` 是 O(n) 全树遍历，`score_nodes()` 里对每个候选又各自遍历一次子孙，整体是**超线性**的。超大页面（几 MB HTML）上提取会明显变慢。有 lxml 时解析提速，但提取的遍历是纯 Python，不受益。
- **预算判定是顺序的**，长页面里靠后的资源更容易拿不到预算。这是确定性换来的代价。

**安全**

- **默认不校验 TLS 证书**（`insecure=True` / `CERT_NONE`）。抓公开网页的实用主义选择，代价是中间人攻击风险。要关掉这个行为：CLI 加 `--verify-tls`，Python API 用 `vault(verify_tls=True)` 或 `fetch(insecure=False)`。
- **`--scripts inline` 会把第三方 JS 原封不动内联进产物**，不做任何改写或净化。
- **`full` 模式默认保留外链 `<script>`**：存档不是一个"安全"的文件，打开它等于从原站加载脚本。
- **`html.parser` 不做 HTML 净化**。产物里的标签来自原始页面，只是被重新序列化。给不可信页面生成产物再拿去展示时，要清楚这一点（reader 模式会删掉 `script`/`iframe`/`object`/`embed` 等，比 full 模式安全得多）。
- **UI 的 `/api/file` 有路径检查**：只允许读 `out_dir` 下的文件（`ap.startswith(out_dir)`）。这是必要的一道闸，但注意它防的是路径穿越，不是"只要在 out_dir 里就安全"。

### `block_text()`：为什么 `res.text` 不能直接拿来比对

`res.text` 是 `normalize_text(root.text_content())` 的结果——空白被压过，整篇正文基本就是**一行**。它适合喂 LLM、算字数、做搜索，但拿来做逐行比对毫无意义：改一个字，整篇就是一行差异，看不出改了哪里。

`block_text()` 的差别只有一处，但很关键：它按 `BLOCK_TAGS`（`p`、`h1`~`h6`、`li`、`blockquote`、`pre`、`td`、`th`、`dd`、`dt`、`figcaption`、`caption`、`summary`）切块，遇到块就把这块的文本收成一行、**不再往下递归**（避免嵌套重复），块与块之间留换行。所以网页里「整段没有换行符」的原始排版不会影响结果——`<p>` 边界本身就是行边界。

这也是 `pipeline` 在记录变更时用 `block_text()` 而不是 `ex.text` 的原因，以及 `cmd_diff()` 抓完页面后必须用**同一个函数**重新提取一遍的原因：两边文本形态不一致的话，每次都会「看起来变了」。

`VaultResult.size()` 的取值逻辑值得注意：**data 模式且 `html` 为空时**返回 JSON 序列化后的字节数，否则返回 `len(self.html.encode("utf-8"))`。

`vault()` 是**唯一的对外编排入口**，`vault_many()` 在 `ThreadPoolExecutor` 里并发调它，并把自己收到的 `keep_site_css` / `show_banner` 原样转发下去。它仍然**没有** `filename` 参数——批量时文件名只能由各页标题生成——也没有转发 `extra_headers` / `verify_tls` / `track_changes`，需要自定义请求头、严格 TLS 校验或关掉变更追踪时得自己写循环调 `vault()`。

`track_changes=True`（默认）让每次成功的 `reader` / `data` 保存在落盘之后把正文记进 `<out_dir>/.webvault/`——实现见 `src/watch.py` 那一节。`full` 模式即使传 `True` 也不会记录；`write=False` 时整段都不执行（没有保存，就没有「上次存的」可比）。`webvault diff` 自己抓页面时就是 `write=False, track_changes=False`——它只做比对，不该顺手改基线。

`VaultResult` 里和变更追踪相关的四个字段：`changed`（这次和上一版比有没有变）、`change_stats`（`added` / `removed` / `old_lines` / `new_lines`）、`first_seen`（是不是第一次记录这个 URL）、`history_key`（归一化之后的键）。`changed` 只在「之前已经有版本」时才可能为真，第一次保存永远是 `first_seen=True` / `changed=False`。

`http_status` / `http_warning` 记录上游的 4xx/5xx：页面照存（`ok=True`），但 `http_status` 非 0、`http_warning` 是一句可直接展示的中文，`summary()` 会追加上一段 `⚠ HTTP 404`。它和 `challenge` / `challenge_advice` 是并列的两类「保存成功了，但你可能存错了东西」信号，区别是后者看的是页面内容，前者看的是状态码。

### `src/discover.py` —— 链接发现

从一个页面（通常是列表页、归档页）里挑出「值得存下来」的文章链接。它**不是爬虫框架**：不递归、不遵守 robots、不做任务队列持久化。

```python

SKIP_PATH_HINTS: tuple
SKIP_TEXT: frozenset

    url: str = ""
    text: str = ""
    score: float = 0.0
    host: str = ""
    same_host: bool = True
    reason: str = ""

    def to_dict(self) -> Dict

def discover(html: str, base_url: str, *, same_host_only: bool = True,
             min_text: int = 6, min_score: float = 8.0, limit: int = 200,
             dedupe: bool = True) -> List[Link]
def discover_from_url(fetcher, url: str, *, same_host_only: bool = True,
                      min_text: int = 6, min_score: float = 8.0,
                      limit: int = 200) -> List[Link]
```

流程是「遍历 `<a>` → 过滤 → 打分 → 排序截断」：

- **范围**：先扫 `<main>` 和 `<article>` 里的链接（这些加 3 分额外权重），再扫整棵树，所以没有语义标签的列表页也能用。
- **过滤在 `_is_skippable()`**：非 `http(s)` 协议、路径含 `/login` `/tag/` `/search` `/about` 这类功能片段、后缀是图片/CSS/字体/压缩包/文档/音视频、路径就是首页、文字为空、文字短于 2 个字符、文字是「首页 / 关于 / 更多 / 下一页」这类功能词的，全部丢掉。
- **打分在 `_score()`**：路径层级（2 层最高，+6）、以 `.html` 结尾（+5）或无扩展名（+2）、有 slug / 数字 ID / 路径里有日期（各 +3）、链接文字够长（+4，超过 12 字再 +2，超过 120 字倒扣 3）、文字里带标点或汉字（各 +1）、同域（+3）。低于 `min_score` 的一律不要。
- **默认只留同域**，`same_host_only=False`（CLI 的 `--any-host`）才收跨域链接；`dedupe=True` 时按 `normalize_url_for_dedup()` 去重，所以 `?utm_source=x` 和 `#anchor` 不会重复。
- 返回的 `Link.reason` 目前恒为 `""` —— 跳过原因只在 `_is_skippable()` 内部用，被跳过的链接不会出现在结果里。

CLI 子命令 `webvault discover` 除了调用它，还负责抓页面、把结果打到终端或 `--json`、写 `--list` 清单，以及 `--save` 时用 `vault_many()` 直接批量保存。

### `src/library.py` —— 离线书库索引

`webvault index` 的实现。扫描输出目录里 WebVault 自己的产物，生成一个同样零外部依赖的 `index.html`（搜索、按类型筛选、按时间/标题/体积/来源站排序都靠内嵌的 `INDEX_JS`）。

```python

    path: str = ""
    rel_path: str = ""
    title: str = ""
    source: str = ""
    host: str = ""
    captured: str = ""
    mode: str = ""

                out_path: str = "", title: str = "WebVault 书库",
                recursive: bool = True, write: bool = True) -> Tuple[str, List[Entry]]
```

两个实现细节值得知道：

- **不重新解析整棵树**。产物动辄几十 MB（图片全是 base64），所以 `_read_meta_html()` 只读文件前 200 KB，用 `_META_RE` 正则从 `<meta name="wv-source|wv-captured|wv-mode|wv-title">` 里取元信息，再从 `<title>`、`wv-meta` 里的斜体摘要、`wv-badge` 里的「正文 N 字」「图 N」补齐标题/摘要/字数/图数。`.json` 产物直接 `json.load()` 读字段。
- **只收自己的产物**。HTML 必须带 `wv-source` 或 `wv-captured`（data 模式的 JSON 除外），且扫描目录根下的 `index.html` 会被跳过——索引页不把自己收进去。

`Entry.mode` 现在三种模式都准：reader / full 的 HTML 模板各自写 `wv-mode`，`.json` 在读的时候直接标成 `data`（见 §7）。`build_index()` 返回 `(索引文件路径, 条目列表)`，`out_path` 既可以是文件也可以是目录（目录时用 `out_name`）。

### `src/watch.py` —— 变更追踪

回答「这个页面什么时候改了」。每次 `reader` / `data` 模式保存成功，`vault()` 把提取出来的正文记一份到输出目录；`webvault diff` 重新抓一次，和最近一版逐行比。差异用标准库的 `difflib`，所以零依赖的承诺还是成立的。

```python

           file_path: str = "") -> Optional[Dict]

```

磁盘布局：

```
<保存目录>/
├── .webvault/
│   ├── history.json          # {"version": 1, "pages": {key: {...}}}
│   └── text/
│       └── a1/
│           └── a1b2c3….txt   # 一个版本一份正文，按内容 sha1 命名
└── 某篇文章.html
```

`history.json` 里每个页面条目是 `{title, last_seen, file, versions: [{hash, captured, bytes, file}]}`。`versions` 按时间往后追加，尾部只保留 `MAX_VERSIONS` 条；正文 hash 没变时不会追加新版本，所以「保存十次但内容没动」仍然只有一个版本。`text/<前两位>/<hash>.txt` 写一次就不再改（同样内容复用同一个文件），滚出 `versions` 的旧文件不会被删除。

几个函数的语义：

- `record()` 写入正文并返回**上一次**的版本信息（没有则 `None`）——调用方据此判断是不是第一次，`pipeline` 就是这么填 `first_seen` 的。
- `last_text()` 取最近一版的正文，`before_hash` 用来跳过刚写进去的当前版本；`history_for()` 取单个 URL 的完整条目，`known_pages()` 返回全部页面的摘要列表（按 `last_seen` 倒序），`webvault diff --list` 打的就是它。
- `key_for()` 用 `normalize_url_for_dedup()` 归一化：去掉 fragment 和 `utm_*` / `fbclid` / `gclid` / `spm` 这类追踪参数，同一个页面从不同渠道进来只算一条记录。
- `normalize_for_diff()` 定义「比对单位」：先按换行分段，再按 `。！？!?；;` 断句，然后把句子合并到每行最多 60 字。不能按原始换行比——网页正文经常整段没有换行符，改一个字就会让整段变成一行差异。
- `diff_texts()` 用 `difflib.SequenceMatcher(autojunk=False)` 拿 opcode，`- ` / `+ ` 前缀和 unified diff 一致；两个改动块相距太远时插一行 `  …`（阈值 `context * 2 + 1`）；输出行数到 `max_lines` 就停，并在末尾补一句「…（差异过多，已截断到 N 行）」。
- `compare()` 返回 `{status, url, diff, stats, since, versions, message}`，`status` 是 `new`（第一次抓，记基线）/ `same` / `changed`。上一版的正文文件丢了（比如手动删了 `text/`）也会退回 `new` 并说明「无法比较，已更新基线」，而不是报错。

`load_history()` 读到坏 JSON 不会让流程失败：直接当空历史重来一份。代价是丢基线，不是丢产物——这个取舍和「永不抛异常」的全局约束一致。`.webvault` 是点开头的隐藏目录，`library.scan()` 会跳掉它，所以它不会变成书库条目。

| `test_friendly_errors(tmpdir)` | 网络错误翻译：DNS 失败 / 连接被拒 / 连接重置 / 超时都要变成中文，且不能带 `URLError` 前缀。重点是 Windows 的中文本地化系统消息（"由于目标计算机积极拒绝"）里没有任何英文关键词，所以必须按异常类型和 `errno` 判断，只靠字符串匹配会漏 |
| `test_thin_content(tmpdir)` | 空壳页识别：一个正文全在 `<script>` 里的大页面要被标成 `thin_content` 并提示可能需要 JavaScript；真正短小但正常的页面不能误伤；`full` 模式不做正文提取，不该报警 |
| `test_online(tmpdir)` | example.com / httpbin / baidu 的真实抓取，**默认不跑**，要加 `--online`（8 项） |

另外三个套件不在 `test_all.py` 里：

| 文件 | 项数 | 说明 |
|---|---|---|
| `tests/test_diff.py` | 16 | 端到端变更检测：起一个内容可变的本地站点，先保存建立基线，再验「没变化 / 加了一段 / 删了一段」三种 diff 输出、`--list` 的清单、版本数在增长且每版都有 hash 和抓取时间、空目录与未知 URL 不崩，以及 `.webvault` 不污染书库扫描 |
| `tests/test_index.py` | 20 | 索引页的 HTML/卡片结构与前端逻辑。JS 用 `node --check` 真跑一遍（搜索、筛选、排序），不是只做字符串检查 |
| `tests/test_ui.py` | 63 | 本地服务集成测试：先起 `webvault-ui.py --port 8774`，端口作为 `argv[1]` 传给脚本；然后通过 HTTP 提交任务、轮询结果、检查产物与 `/api/file` 的路径限制，并验证非法参数不炸 |

`tests/check_selfcontained.py` 不是断言套件，是一次**自包含审计**：用真解析器按「标签 + 属性」列出 `examples/` 下所有产物里会发起网络请求的地址，确认它们要么是 `data:`、要么是页内锚点、要么是相对链接。当前 `examples/` 是 0/6——6 个产物里没有一个带真实外链。项目里有它是为了防止「产物自包含」这个承诺悄悄退化。

关键设计：`test_inline_offline()` 用 `_FakeInliner(Inliner)` **子类重写 `_get()`**，从字典里取数据而不碰网络。这是内联层最好用的测试接缝——`_get()` 是唯一的网络出口，覆盖它就能完整测试 CSS 重写和预算逻辑。

测试辅助是 `check()` / `eq()` / `no_raise()` / `group()`，手写的极简断言，没有用 `unittest` 或 `pytest`——同样是零依赖承诺的延伸。

```bash
python tests/test_all.py            # 离线全套（332 项）
python tests/test_all.py --online   # 额外跑真实站点（340 项）
python tests/test_diff.py           # 变更追踪端到端（16 项，自己起本地站点）
python tests/test_index.py          # 索引页与前端逻辑（20 项）
python tests/test_ui.py 8774        # 本地服务集成测试（63 项，服务要起在临时目录上）
python tests/check_selfcontained.py # 自包含审计（不是断言套件）
```

套件会在临时目录（`webvault-test-*`）里操作，退出码 0 = 全部通过，1 = 有失败项并列出失败清单。

`tests/chk_*.py` 是开发期间的探针脚本（`chk_ab` / `chk_ext` / `chk_skip` / `chk_webp`），用来手工验证某个现象——`chk_ext.py` 扫 `examples/` 里的产物找残留外链，其余几个会真的发网络请求。它们不属于回归测试，也不会在套件里被执行。
